## Design conclusions before implementation

1. OAuth binding is a separate authenticated GuideIn operation. Preparation returns an installation URL and a PKCE authorization URL. Completion requires the same GuideIn subject/tenant, unexpired unused state, the original verifier, provider user identity and membership in the requested installation, plus a current app-level installation lookup. Installation query parameters alone confer no authority. Keep user tokens only for this exchange.
2. A minimal global routing/transport registry is necessary before tenant binding. It stores only installation routing, delivery identifiers/digest/status, and bounded notification selectors; no repository source, free text, file data or provenance. Tenant-owned installation/access/change/provenance/CI rows retain FORCE RLS. Only securely bound routing may select a worker tenant. Unknown installation receipts await binding and trigger a canonical reconciliation after binding.
3. The acceptance transaction includes receipt + existing queue intent + existing outbox event for bound work. 2xx follows commit. Unknown signed events are durably IGNORED, not normalized. Delivery ID conflicts with different content are not silently reinterpreted.
4. Provider reads occur outside long database transactions, under a bounded per-installation processing lease. Every request rechecks access; final persistence rechecks the installation generation and job lease. Restrictive lifecycle updates increment generation so in-flight fetches cannot commit after revocation. New authority requires canonical reconciliation.
5. Normalization writes provider-neutral records atomically with outbox and acknowledgement. PR identity includes exact head SHA; repository identity uses external numeric ID, never slug. Hydration checks the PR head again after the paginated file listing, then verifies the fetched commit's exact SHA. Incomplete/capped results are explicit.
6. Phase-1 queue needs additive deadline-aware failure scheduling and typed claims, not a replacement queue. Existing entry points and their 80 regression cases must remain intact. Provider retries belong in durable available_at, not HTTP loops (except a single 401 refresh for idempotent GET).
7. Proof uses real GuideIn HTTP and PostgreSQL 18 with simulated GitHub HTTP. No live account or write permission is necessary. A provider fixture passing is not evidence of RLS, durable acceptance, or crash recovery; those require the real database/restart suite.
